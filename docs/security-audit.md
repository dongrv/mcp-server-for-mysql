| Two same-engine source IDs accidentally share one physical database | MySQL integration fixture | Run orders and logs in independent MySQL containers with distinct loopback-only, environment-overridable host ports, databases, test users, authenticated database-specific health checks, and named data volumes | `TestIntegrationComposeUsesLoopbackParameterizedPorts`; `TestIntegrationComposeUsesAuthenticatedDatabaseHealthChecks`; `TestMultipleSameEngineSourceProfiles` checks different server UUIDs, exact database names and marker rows, and MySQL 1146 cross-source table failures |
| Connection details leak through source discovery | `list_sources` integration response | Marshal the live three-source response and expose only ID, engine, and business profile fields | `TestMultipleSameEngineSourceProfiles` rejects DSN, host, user, password, pool, capability, and fixture-port data |

The server accepts only configured source IDs and exact environment-reference DSNs, parses SQL by dialect, and rejects unsupported, session, transaction, external-table, locking, stateful, and comment-only input. Runtime diagnostics omit SQL, parameters, results, DSNs, hostnames, and credentials.

Source metadata has a separate trust boundary from execution identity. Profiles can become stale and their business terms can overlap, so a client must not infer a unique target when several candidates are plausible. It must show candidate `display_name` and `description` values and wait for an explicit user choice. Execution is controlled only by the exact `source_id` returned as `id` from `list_sources`; the display name is response-only context and does not bind or alter `preview_hash`.

The live integration fixture exercises this boundary with three sources: `orders` and `logs` are independent MySQL 8.4 containers, while `analytics` is ClickHouse. Exact `source_id` queries reach source-specific marker rows and database names; querying either MySQL marker table through the other exact ID fails, and the two servers report different UUIDs. Passing the display name `订单库` as `source_id` is rejected as unknown. The same test verifies sorted discovery profiles and marshaled-output redaction. This proves execution isolation for the fixture, but it does not make metadata authoritative: overlapping descriptions, aliases, or keywords still require the client to present candidates and let the user choose.

Stale profile metadata remains a residual risk. An exact source ID can continue to route correctly even when its display name or business description no longer reflects the database contents. Profile ownership, review cadence, and client-side user confirmation remain operational controls outside the MCP server.

Residual risk is intentional: a matching hash proves only that an execution request matches its preview. A direct caller can replay a previously obtained hash, and the MCP process cannot prove a human approved it. An upstream gateway must authenticate users, authorize source/action access, display previews, consume approvals once, prevent replay, and persist audit records. See `prd/2026-07-14-wecom-database-gateway-prd.md`.

Integration uses `docker-compose.integration.yml` and `RUN_DATABASE_INTEGRATION=1 go test -tags=integration ./internal/integration -count=1`. Docker was initially blocked in this environment because its configured registry mirror could not resolve through DNS. Docker is now reachable and fixture startup succeeds; a future mirror-DNS image-pull failure is infrastructure failure, not an MCP test result.
