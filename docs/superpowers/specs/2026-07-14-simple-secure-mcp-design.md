# 简洁、安全的多数据源数据库 MCP 设计

## 1. 目标

当前项目重构为面向团队的数据库 MCP Server，优先帮助程序员、策划和 QA 在已知表结构的前提下快速查询、聚合和查看少量样例数据。它支持 MySQL 与 ClickHouse 的多个配置实例，并保留受控的结构和数据变更能力。

产品应当开箱即用：使用者只需要理解数据源名称、一个查询工具和少数结构工具。安全规则由服务默认执行，不要求使用者配置复杂的身份、权限、审计或网关组件。

## 2. 非目标与边界

本项目不是企业身份系统、权限系统、审计平台、数据导出平台或自然语言数据库代理。

下列职责明确不属于本项目：

- 企业微信接入、WebSocket 会话与用户身份获取。
- 用户、角色、授权令牌、确认记录和审计日志的持久化。
- 查询结果脱敏、行级权限或列级权限。
- 大量结果导出、文件保存和下载。
- 按业务词搜索未知表或生成业务知识图谱。

未来上游网关可负责真人确认、身份授权和审计。当前 MCP 是中立、无持久化状态的数据库执行组件；连接池及一次请求内的临时对象不构成状态存储。

## 3. 用户与核心工作流

### 程序员

已知表后查看字段和索引，执行带参数查询、聚合、分页和 `EXPLAIN`，快速验证数据与 SQL 行为。

### 策划

在明确限制条件后查看少量真实结果或聚合统计，核对业务配置是否符合预期。

### QA

执行可复现的限制条件查询，检查测试数据、异常数据和变更后的结构，并取得可定位的错误信息。

### 查询流程

1. 调用 `list_sources` 选择数据源。
2. 必要时调用 `describe_table` 确认字段、索引和能力。
3. 调用 `query` 执行只读查询、聚合或样例预览。
4. 服务返回有限、结构化且可截断的结果。

## 4. 对外工具模型

工具数量应保持少而稳定。工具的参数和返回值使用 JSON Schema 约束；所有工具都带 `source_id`，且源 ID 必须存在于配置中。

| 工具 | 目的 | 执行规则 |
| --- | --- | --- |
| `list_sources` | 枚举可用数据源的 ID 和类型；数据源 ID 本身应使用可理解的业务名称 | 不返回主机、库名或凭据 |
| `describe_table` | 返回指定表的字段、索引和必要结构信息 | 只读 |
| `query` | 运行查询、聚合、样例预览和 `EXPLAIN` | 只接受可识别的只读语句 |
| `execute_sql` | 高级入口，运行原生 SQL（可多语句） | 统一安全分析和确认；上游应限制调用资格 |
| 高层表/字段/索引工具 | 建表、字段、索引、复制、重命名与迁移 | 结构化参数生成 SQL，统一安全分析和确认 |

现有的表、字段、索引、复制/重命名和迁移工具保留其业务能力，但内部不再独立拼接并执行 SQL。它们只生成受控操作，再交给统一的执行编排层。

`query` 的参数值允许 JSON 基础类型，不能再局限于字符串。服务对查询设置固定的安全默认值：上下文超时、最大返回行数和最大语句数。若结果被截断，响应必须明确标识 `truncated: true`；不自动脱敏或改变返回列。

## 5. 执行模式与无状态确认

服务配置 `mode`，只支持：

- `quick`：只读查询和低风险写入直接执行；高风险操作先预览。
- `strict`：所有 SQL 先预览，二次请求确认后执行。

默认模式是 `quick`，以保证高频查询流畅；涉及破坏性或高影响操作时仍然强制确认。

高风险至少包括：`DROP`、`TRUNCATE`、无 `WHERE` 的 `DELETE` 或 `UPDATE`、所有 `ALTER`、迁移、重命名。方言无法可靠识别或分类的 SQL 也视为不可执行，而非当作低风险处理。

确认协议不保存服务端状态：

1. 首次调用使用 `confirm: false` 或省略该字段。若当前模式要求确认，服务生成完整 SQL、风险摘要和 `preview_hash`，并不执行。
2. 调用方在获得真人确认后，以完全相同的结构化参数或原生 SQL 再次调用，并提供 `confirm: true` 与 `preview_hash`。
3. 服务重新生成和规范化 SQL，计算绑定数据源、工具、SQL 语句顺序及参数的哈希。哈希不一致则拒绝；一致才执行。

该机制保证确认对象不会被调用方在二次调用中悄悄改写，但不证明确认者是人，也不防止重放。企业网关项目负责真人确认、身份验证、单次消费和审计；其 PRD 见 `docs/prd/2026-07-14-wecom-database-gateway-prd.md`。

多语句仅在 `execute_sql` 中允许。服务先按方言安全拆分和完整分析；任一语句需要确认时，整组 SQL 都需要确认。确认哈希包含完整语句列表及顺序。

## 6. 极简配置

配置采用单个 YAML 文件，连接串通过环境变量插入。使用者只需要配置模式与数据源；资源限制使用安全内置默认值，只有将来确有需要时才增加可选高级覆盖项。

```yaml
mode: quick

sources:
  - name: orders
    type: mysql
    dsn: ${ORDERS_MYSQL_DSN}

  - name: analytics
    type: clickhouse
    dsn: ${ANALYTICS_CLICKHOUSE_DSN}
```

约束：

- `name` 是稳定且唯一的 `source_id`，并应使用可理解的业务名称以帮助调用方选择数据源。
- `type` 当前只能是 `mysql` 或 `clickhouse`。
- `dsn` 支持 `${ENV_NAME}` 形式的环境变量引用；缺失变量、空 DSN、未知类型或重复名称均使启动失败。
- `list_sources` 从配置派生可见数据源；连接详情和凭据永不返回。

部署文档必须建议每个数据源使用最小数据库权限账号。这是当前 MCP 无用户权限模型下防御误用的最后一道边界。

## 7. 内部架构

### 配置与数据源

- `config`：读取、插值、验证 YAML，输出不可变的配置对象。
- `datasource`：按源 ID 管理连接池生命周期。
- `adapter`：每个数据库方言实现连接、元数据、标识符引用、语句分析、查询、执行和能力声明。

MySQL 与 ClickHouse 分别实现适配器。通用层依赖接口而非驱动，实现新增数据库时只增加新适配器，避免在工具处理器中出现方言 `switch`。

### 操作与安全

- `operation`：高层工具将结构化输入转换为数据库无关操作意图。
- `planner`：适配器将操作意图生成 SQL；原生 SQL 则进入对应方言分析器。
- `policy`：根据模式和语句风险决定执行或预览。
- `preview`：生成稳定的 SQL、摘要、风险和哈希。
- `executor`：在带超时的上下文中执行，关闭资源并归一化结果和错误。

所有可执行操作必须通过 `planner -> policy -> executor`。禁止高层工具自行调用驱动，也禁止在输入中直接用字符串格式化不受验证的标识符或类型。

### MCP 传输

`mcp` 包仅负责 JSON 参数解码、调用用例和返回一致的结构。它不持久化用户、会话、确认或审计信息。上游可把企业身份等上下文用于自身逻辑，但当前 MCP 不依赖它。

## 8. 方言、解析与 SQL 安全

SQL 参数必须通过数据库驱动的参数绑定传递。标识符不能参数化，必须由适配器校验后进行正确的方言引用。禁止复用当前项目中 `fmt.Sprintf` 拼接表名、列名、索引名或列定义的做法。

原生 SQL 需要使用成熟、可维护的方言解析能力，至少能安全完成语句拆分、类型分类、只读识别和关键风险规则。若解析库或适配器无法理解某条语句，服务返回明确的“不支持/无法安全判定”错误；不得以字符串前缀匹配替代解析。

`query` 只允许方言定义的读取语句，例如 `SELECT`、只读 `WITH`、`SHOW`、`DESCRIBE` 和 `EXPLAIN`。任何可能写入、调用副作用函数、修改会话或包含未知语句的查询请求均拒绝。查询行数限制在生成 SQL 或执行阶段可靠落实，结果响应不允许无限制读取到内存。

## 9. 错误、稳定性与可观测性

对调用方输出稳定的错误码、简短消息和 `request_id`。原始 DSN、密码、主机名及低层驱动敏感详情不得出现在响应中。错误类别至少包括：配置错误、未知数据源、参数错误、方言不支持、风险确认缺失、预览不匹配、查询超时、连接失败和数据库执行错误。

服务输出面向部署者的结构化日志，但不持久化审计记录。日志中不得记录 DSN、密码和完整结果集；完整 SQL 仅在明确的调试开关下才允许输出，并须在文档中标明风险。

连接池在启动时建立并健康检查，在关闭时幂等释放。请求上下文控制连接、查询和扫描过程；所有 `Rows`、事务和临时资源必须关闭。服务在连接失败、配置错误、超时和取消时应快速失败，不能遗留事务或阻塞其他请求。

## 10. 测试与验收

### 单元测试

- YAML、环境变量插值、重复源和非法源配置。
- 数据源查找与适配器能力判断。
- 标识符校验与引用，覆盖注入载荷。
- SQL 风险分类、只读限制、未知语句拒绝和多语句整体判断。
- 快捷/严格模式、预览哈希一致性和二次确认。
- 查询上限、截断结果、超时和错误归一化。
- 每项高层工具生成的 SQL 与参数绑定。

### 集成测试

- 使用真实 MySQL 与 ClickHouse 测试环境验证连接、元数据、查询、结构操作和异常路径。
- 验证默认模式下高风险操作不在预览请求中执行。
- 验证确认内容改动、跨数据源确认和多语句局部改动均被拒绝。
- 验证连接池关闭、上下文取消和并发请求不会泄漏资源或交叉数据源。

### 已知问题记录

新增安全审计文档，记录当前发现的问题、影响、修复设计、验证用例和未解决风险。至少覆盖任意 SQL 绕过、标识符 SQL 注入、确认缺失、无界查询、事务清理、配置不一致、健康检查错误和无测试覆盖等现状。

## 11. 实施顺序

1. 建立配置、数据源注册表和 MySQL/ClickHouse 适配器接口。
2. 建立统一 SQL 计划、安全策略、预览哈希和执行编排。
3. 重构查询、元数据和现有高层工具以接入编排层。
4. 实现 ClickHouse 适配器及能力限制。
5. 增加单元/集成测试和安全审计文档。
6. 更新 README、示例配置和迁移说明。
